Hierarchical Decision Processes¶

Similar to how complex programs are decomposed into functions, a complex Decision Process (DP) is often decomposed into multiple DPs. Since a Cognitive Agent (Cogent) has a single “root” DP, process decomposition thus naturally produces a hierarchy. And as with function decomposition, hierarchical DPs commonly produces multiple benefits, including…

  • DP re-use: a single decision process can be called upon in multiple contexts, possibly with re-parameterization (e.g., via supplied arguments)

  • State/logic simplification: each sub-process focuses solely on those state features that are necessary

    • As a bi-product, testing becomes simplified as well!

In the code below, an agent assists a Bingo caller in keeping track of drawn balls:

  2Illustrates a simple hierarchical
  3decomposition of decision processes
  4in a Bingo caller assistant.
  5
  6Sub-problem of getting valid input

  9duplication and interactive game state.

257@dp_play.operator("draw")
258class PlayDraw(Operator[PlayState]):
259    """draw the next spot"""
260
261    @override
262    def can_perform(self, state: PlayState, _io: IOContainer) -> bool:
263        return state.next_call is None
264
265    @override
266    def perform(self, state: PlayState, _io: IOContainer) -> None:
267        while True:
268            letter = get_valid_input(None)
269            number = get_valid_input(letter)
270
271            candidate = f"{letter}{number}"
272            if candidate not in state.called:
273                break
274
275            print(f"Already called: {candidate}")
276
277        state.next_call = candidate
278

280@dp_play.operator("announce")
281class PlayAnnounce(Operator[PlayState]):
282    """announce the draw"""
283
284    @override
285    def can_perform(self, state: PlayState, _io: IOContainer) -> bool:
286        return state.next_call is not None
287
288    @override
289    def perform(self, state: PlayState, _io: IOContainer) -> None:
290
291        # excuse the nested operator logic
292        # for a shorter example
293        result = input(f"Draw {state.next_call} (bingo?): ")
294        if result.strip().lower() == "bingo":
295            print(f"Prior: {state.called}")
296
297            confirm = input("Confirmed (y/n)? ")
298            if confirm.strip().lower() == "y":
299                state.done = True

302        state.next_call = None

Root DP: Ball Draw <-> Game-Win Verification¶

The cogent primarily operates within a logical loop:

  1. Call the next drawn ball

    1. Verified as a valid letter-number combination

    2. Confirmed as not having been called before

  2. If “Bingo!” is claimed, providing prior draws for confirmation

    1. If confirmed, done

    2. Otherwise, back to #1

This is encoded as the dp_play DP.

Tip

In practice, decision process decomposition invites decomposition into separate files/folders (e.g., folder for the DP, with files for state, operators, support functions, etc.).

Sub-Process: Validate Call (1.1)¶

Nested within the root DP is the need to verify a valid letter and associated number:

    BOUNDS: ClassVar[dict[str, tuple[int, int]]] = {
        "B": (1, 15),
        "I": (16, 30),
        "N": (31, 45),
        "G": (46, 60),
        "O": (61, 75),
    }

Errors include…

  • An invalid letter

  • Given a letter, an invalid number

  • A previously called combination (signaling full re-entry needed for a typo that produced a valid combination)

This sub-process is encapsulated within a function…

ARG_LETTER: str = "letter"
"""name of the argument to supply to the sub-problem"""


def get_valid_input(letter: str | None) -> str:
    """
    convenience method to provide the
    letter as the appropriate argument
    to the sub-dp and extract the result
    """

    dp_input.reinit()
    result = dp_input(max_cycles=None, suppress_errors=True, **{ARG_LETTER: letter})

    assert result is not None

    return cast(str, result.utterance)

The letter argument parameterizes the dp_input DP’s operators:

  • The GetInput operator’s prompt (“letter” vs “number”)

  • The choice of validation operator (via can_perform): ValidateInputLetter vs ValidateInputNumber

This function is called within the perform method of the root DP’s PlayDraw operator.
